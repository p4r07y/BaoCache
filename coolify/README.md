# WordPress V4 — DigitalOcean Managed MySQL + Coolify

Production-oriented WordPress stack for a Coolify VPS:

```text
Cloudflare → Coolify proxy → Nginx FastCGI cache → PHP 8.5-FPM / WordPress
                                                      ├─ Managed MySQL (TLS)
                                                      └─ Redis object cache
```

MySQL does not run on the VPS. DigitalOcean manages the MySQL cluster, backups,
PITR, failover and scaling. The VPS runs Nginx, PHP-FPM, WordPress cron and Redis.

## Included

- PHP 8.5-FPM Alpine, OPcache and a tuned FPM pool.
- Nginx gzip, static asset cache, security rules and FastCGI page cache.
- Redis with password, LFU eviction and no persistence (cache only).
- Dedicated WordPress cron worker every minute for reliable scheduled cache work.
- DigitalOcean Managed MySQL over TLS.
- DigitalOcean CA installed in the container trust store at startup.
- Managed MySQL/TLS diagnostic script.
- Repository-managed WordPress plugins synchronized on every WordPress start.
- Eight persistent WordPress authentication keys/salts generated by Coolify.
- Security headers, bounded container logs and process limits.
- No host bind mounts for configuration files; configs are baked into images.

## 1. Create DigitalOcean Managed MySQL

Create a MySQL cluster in the same region as the Coolify VPS. In the database
**Network Access / Trusted Sources** page, add the Coolify Droplet. Download the
CA certificate from **Connection Details**.

Use the connection values shown by DigitalOcean:

```text
DB_HOST=dbaas-db-....db.ondigitalocean.com:25060
DB_NAME=defaultdb
DB_USER=doadmin
DB_PASSWORD=the-managed-database-password
```

`DB_HOST` must contain only `hostname:25060`. Do not include `mysql://`, username,
password, database name, spaces or quotes.

Use the private hostname only when the VPS and database can communicate through
the same DigitalOcean VPC. Otherwise use the public hostname and restrict access
with Trusted Sources.

## 2. Add plugins

Redis Object Cache 2.8.0 is already downloaded from WordPress.org during the
image build, verified with SHA-256, synchronized into the persistent volume and
activated automatically on an existing installation. The PhpRedis extension and
`object-cache.php` drop-in are also bundled, so do not upload another Redis cache
plugin or click **Enable Object Cache** manually.

To upgrade Redis Object Cache later, update both `REDIS_CACHE_VERSION` and
`REDIS_CACHE_SHA256` in `php/Dockerfile`, then rebuild. Updating this
repository-managed plugin only in wp-admin is not persistent across deployments.

Extracted plugin folders are recommended:

```text
wordpress/plugins/your-plugin/your-plugin.php
```

Commit the folders to a private repository and redeploy. V4 copies new and changed
files into the persistent WordPress volume every time the `wordpress` service
starts. It deliberately does not delete plugins removed from Git. Delete those
through wp-admin after taking a backup.

`power-schedule-manager` and the independent `baocache` plugin are bundled in
this repository and listed in `AUTO_ACTIVATE_BUNDLED_PLUGINS`. On an existing
WordPress installation they are activated safely after synchronization. On a
brand-new installation, finish the WordPress setup first, then activate them in
wp-admin or restart the WordPress service once. Activation never deletes the
database, uploads or existing plugin data.

`baocache` is a local administration layer for the existing Nginx FastCGI and
Redis Object Cache architecture. It does not add another WordPress HTML cache
and does not depend on `power-schedule-manager` or a specific theme. Its initial
feature set includes safe core reductions, WordPress
native defer strategies, context-aware asset rules, resource hints and optional
`X-Accel-Expires` TTL suggestions. Configure it from the **BaoCache** menu after
the first WordPress login. Script and asset rules should always be tested on
staging before being enabled on the public site.

BaoCache `0.3.0-beta.78` adds evidence-driven **Automatic Critical Images**
plus a bounded Data Retention and Database Health maintenance layer.
It ranks bounded same-site `<img>` candidates from the public front-page DOM,
without storing raw HTML or claiming that a candidate is the measured LCP.
Applying a candidate is limited to front-page preload, eager loading and high
fetch priority. A public post-change probe must verify all three outputs or the
plugin immediately restores the previous configuration; a stale-safe manual
rollback remains available afterwards.

Settings → Advanced keeps configuration after uninstall by default while always
removing disposable runtime queues, locks, transients and cron. Diagnostics
history can be retained separately, or an explicit destructive policy can
remove every registered BaoCache option. Diagnostics → Database Health checks
only BaoCache-owned schema/configuration/cron state and exposes a read-only
autoload-size inspector; it never repairs or deletes WordPress content or data
owned by another plugin.

Its product position and evidence-based release plan are documented in
[`docs/BAOCACHE-ROADMAP.md`](docs/BAOCACHE-ROADMAP.md). BaoCache never reports
FastCGI hit ratios, Redis latency or Core Web Vitals unless those values come
from a real configured data source.

BaoCache also provides opt-in WordPress hardening controls. It can reduce XML-RPC,
self pingback, trackbacks, legacy discovery links, shortlink/generator output,
Application Passwords and the built-in file editor. Attachment and author
redirects are off by default. When Wordfence is active, BaoCache explains that
firewall, malware scan, login security, 2FA and brute-force protection remain
Wordfence responsibilities. Security response headers are managed by the
bundled Nginx image and verified through Header Inspector.

The Docker/Coolify/Nginx/PHP/Redis compatibility contract and deployment checks
are in [`docs/BAOCACHE-INFRASTRUCTURE.md`](docs/BAOCACHE-INFRASTRUCTURE.md).

FastCGI 24-hour analytics and purge authentication use private BaoCache volumes.
The small `baocache-secrets` service creates the metrics token and Nginx purge
password once, on the first deployment. No Coolify variable is required and no
secret is baked into an image, committed to Git or exposed publicly. WordPress
can only read the generated values; Nginx has a separate read-only secret mount.

The Nginx image compiles the pinned `ngx_cache_purge` module against Nginx 1.28.
BaoCache can then purge one exact same-site URL after a post is saved, or through
its admin control. It never exposes wildcard or full-cache purge in wp-admin,
and it never removes Nginx cache files from PHP.

V4 also accepts plugin ZIP files placed directly in `wordpress/plugins/`. They are
automatically extracted while building the image. A folder is still preferred
because its contents and version changes are visible in Git.

During startup, logs show one line for every detected plugin:

```text
Bundled plugin synchronized: redis-cache
```

If the log says no bundled plugin was found, the plugin was not present in the Git
branch/build context used by Coolify. Confirm that it was committed to `main` and
is not excluded by `.gitignore`.

Do not put licence keys or other secrets in the repository.

## 2.1. Blocksy child theme

`wordpress/themes/cupdienlamdong` is bundled and synchronized on every WordPress
container start. If the `blocksy` parent theme is already installed, the child
theme is activated automatically on an existing WordPress installation. On a
new site, install Blocksy from **Appearance → Themes**, finish WordPress setup,
then restart the WordPress service once.

On its first activation the child copies existing `theme_mods_blocksy` values so
the current Blocksy Customizer layout is preserved. Business logic remains in
`power-schedule-manager`; only presentation overrides belong in the child theme.

## 3. Create the Coolify resource

1. Push this repository to Git.
2. In Coolify create a **Docker Compose** resource from the repository.
3. Set the Compose path to `/docker-compose.yml`.
4. Configure the public domain on service **nginx**, port **80**.
5. Set the health-check path to `/healthz`.
6. Do not expose `wordpress`, `wordpress-cron` or `redis`.
7. Keep **Connect to Predefined Network** disabled. The Compose file deliberately
   does not declare a custom network; Coolify creates the shared application
   network used by `nginx`, `wordpress`, `wordpress-cron` and `redis`.

## 4. Add Coolify environment variables

Create these Production variables. They are needed at runtime only; Buildtime can
remain disabled.

| Name | Value |
| --- | --- |
| `WP_HOME` | `https://example.com` |
| `WP_SITEURL` | `https://example.com` |
| `DB_HOST` | DigitalOcean hostname plus `:25060` |
| `DB_NAME` | Usually `defaultdb` |
| `DB_USER` | Usually `doadmin`, or a dedicated database user |
| `DB_PASSWORD` | Managed MySQL password |
| `DB_SSL_CA` | Complete downloaded DigitalOcean CA certificate |
| `WP_DEBUG` | `false` |

### Optional: BaoCache Cloudflare read-only audit

This audit is disabled by default. It verifies a Cloudflare API token and reads
the status of one Zone only. It does not purge cache or manage Cache Rules, DNS,
WAF, SSL, Workers or APO. Add these **runtime** variables in Coolify:

| Name | Coolify value |
| --- | --- |
| `BAOCACHE_CLOUDFLARE_AUDIT_ENABLED` | `true` |
| `BAOCACHE_CLOUDFLARE_ZONE_ID` | The 32-character Zone ID for this site |
| `BAOCACHE_CLOUDFLARE_API_TOKEN` | A **Coolify Secret** — never a normal Git value |

Scope the token to this one Zone with **Zone → Zone → Read**. The audit does not
need Cache Purge permission. Do not put the token in wp-admin, `wp-config.php`,
plugin settings, a JSON export, source control, or a build argument. A future
separate purge feature, if explicitly enabled, must use a distinct least-privilege
token and is not part of this audit.

See [`docs/BAOCACHE-CLOUDFLARE-AUDIT.md`](docs/BAOCACHE-CLOUDFLARE-AUDIT.md) for
the exact flow and failure diagnostics.

Các token nghiệp vụ của Power Schedule Manager (XoSoAPI, nguồn giá, Turnstile,
bản đồ, OneSignal, Telegram, webhook, Zalo và backup) vẫn được quản lý trong
**Trung tâm vận hành** của plugin đó. Chúng là một phạm vi độc lập với BaoCache.
Không nhập Cloudflare token dùng cho BaoCache audit vào Power Schedule Manager
và không nhập token đó vào wp-admin.

Nếu Power Schedule Manager đang dùng Cloudflare cho một tác vụ riêng, giữ token
đó tách biệt với token BaoCache. Chỉ chuyển nó sang Coolify Secret sau khi đã
kiểm tra chính xác quyền và endpoint mà Power Schedule Manager đang sử dụng.

## 4.1. Push Git và Coolify prebuild

Coolify build image trực tiếp từ commit Git. Không cần build local trước khi
deploy; Docker build của service `wordpress` đã tự PHP-lint các plugin được
bundle, gồm BaoCache. Repository cũng có workflow GitHub Actions **Coolify
prebuild**: render Compose, kiểm tra cú pháp shell/PHP/Python, rồi build Nginx,
PHP/WordPress, Redis, metrics và secrets trước khi một commit được merge vào
`main`.

Push vào Git các file nguồn và cấu hình sau:

```text
docker-compose.yml
php/  nginx/  redis/  metrics/  secrets/
wordpress/plugins/  wordpress/themes/
docs/  README.md  .env.example
```

Không push `.env` thật, token Cloudflare, mật khẩu database/Redis, WordPress
keys/salts hay dữ liệu volume. `.env` đã được `.gitignore` loại trừ; chỉ giữ
`.env.example` với giá trị rỗng/mẫu. Sau mỗi thay đổi Docker, Nginx, PHP hoặc
plugin, push commit, chờ workflow **Coolify prebuild** xanh rồi chọn **Redeploy**
trong Coolify. Nếu không dùng GitHub, chạy cùng hai bước trong CI của Git provider:
`sh scripts/validate.sh` và `docker compose --env-file .env build`.

Sau deploy staging, chạy `sh scripts/smoke-test.sh https://staging.example.com`
để xác nhận request ẩn danh thứ hai thực sự trả `X-FastCGI-Cache: HIT`. Checklist
đầy đủ, không chứa secret, ở [staging acceptance](docs/BAOCACHE-STAGING-ACCEPTANCE.md).

BaoCache Browser Resource Timing mặc định tắt. Nếu cần dữ liệu browser tổng hợp
để điều tra Assets, bật opt-in trong tab **Assets → Analysis**; chính sách dữ
liệu và giới hạn mẫu ở [frontend metrics](docs/BAOCACHE-FRONTEND-METRICS.md).

Delay JavaScript có preview riêng 30 phút cho đúng quản trị viên đang đăng nhập;
không bao giờ ảnh hưởng khách truy cập trong lúc thử. Cách dùng ở
[Delay preview](docs/BAOCACHE-DELAY-PREVIEW.md).

For `DB_SSL_CA`, use Coolify **Normal view**, enable **Multiline**, then paste:

```text
-----BEGIN CERTIFICATE-----
...complete certificate...
-----END CERTIFICATE-----
```

Do not add quotes. Current Coolify versions treat multiline values literally
automatically, so the separate Literal option may be hidden. V4 also accepts
legacy values containing literal `\n` characters or a base64-encoded PEM, but
pasting the downloaded PEM directly is preferred.

The database table prefix is generated automatically and persistently by Coolify:

```text
wp_${SERVICE_USER_TABLEPREFIX}_
```

Coolify replaces `SERVICE_USER_TABLEPREFIX` with a random 16-character value.
Do not create `WORDPRESS_TABLE_PREFIX` manually. The generated prefix remains
stable across redeployments of the same resource.

Coolify also automatically creates eight independent 64-character WordPress
authentication keys and salts. They appear as `SERVICE_PASSWORD_64_WP_*` variables
and stay stable across redeployments. Do not replace or delete them after users
have logged in, because changing them signs every WordPress session out.

Redis credentials and its cache namespace are also generated automatically:

```text
SERVICE_PASSWORD_64_REDIS
SERVICE_USER_REDISPREFIX
```

The effective WordPress cache prefix becomes:

```text
wp_<random-16-character-value>:
```

Do not manually create `REDIS_PASSWORD` or `REDIS_PREFIX`. Coolify creates and
reuses the magic variables above for both the Redis and WordPress containers.
Changing the generated prefix/password later clears the effective object-cache
namespace but does not affect Managed MySQL data.

## 5. Deploy and verify

Deploy only after all required variables exist. When deployment finishes, open a
terminal for the `wordpress` service and run:

```sh
php /usr/local/bin/check-managed-db.php
```

Success looks like:

```text
OK: Connected to Managed MySQL using TLS cipher ...
```

Common errors:

- `2002` or timeout: incorrect host/port, Trusted Sources, firewall or VPC choice.
- `1045`: incorrect user or password.
- `1049`: incorrect database name.
- CA/PEM error: paste the complete downloaded certificate in Normal view with
  Multiline enabled. Do not paste the certificate filename.

Then open the public domain and finish the normal WordPress setup. Redis object
cache is already enabled by the bundled drop-in. On a brand-new installation,
restart the WordPress service once after setup if the Redis Object Cache plugin
is not yet shown as active; object caching itself does not require that restart.

## Cache behavior

FastCGI cache is enabled for logged-out GET/HEAD requests without a query string.
It bypasses wp-admin, login, REST API, cron, carts, checkout, accounts and logged-in
or WooCommerce sessions. Inspect the `X-FastCGI-Cache` response header:

- `MISS`: generated by WordPress and stored.
- `HIT`: served by Nginx cache.
- `BYPASS`: intentionally not cached.

The default cache lifetime is ten minutes. Public pages backed by
`power-schedule-manager` send `X-Accel-Expires` and use a 60-second micro-cache,
so imported schedules, lottery, weather and market data converge quickly without
requiring an Nginx purge module. Cloudflare exact-URL purge remains optional.

BaoCache also exposes a 24-hour **FastCGI BYPASS diagnostics** panel from its
private Nginx observer. It counts only a bounded cache-skip category: non-GET/HEAD
method, query string, excluded path, session/login cookie or Authorization header.
It never records a URL, query string, cookie value, Authorization value or visitor
identifier. These categories describe intentional cache bypasses; they are not an
error or a PageSpeed score.

## Content Security Policy

CSP is managed at Cloudflare rather than duplicated in Nginx. Apply
`docs/cloudflare-csp-report-only.txt` to the Cloudflare Report-Only response
header and follow `docs/CSP.md` before promoting it to enforcement. For
BaoCache Analytics, the Cloudflare rule must allow `www.googletagmanager.com`
and `www.clarity.ms` in `script-src-elem`; add
`www.googletagmanager.com` to `frame-src` for the GTM noscript iframe.

The named `wordpress_data` volume is the source of persistent WordPress files.
Image rebuilds refresh bundled plugin and child-theme code into that volume; they
do not replace Managed MySQL data, uploads or runtime configuration.

## Redis host warning

If Redis logs:

```text
Memory overcommit must be enabled
```

run on the VPS host:

```sh
sudo sysctl -w vm.overcommit_memory=1
echo 'vm.overcommit_memory=1' | sudo tee /etc/sysctl.d/99-redis.conf
```

Redis is used only as a disposable cache; MySQL remains the source of truth.

## Optimize Wordfence Firewall

V4 supports Wordfence Extended Protection with Nginx and PHP-FPM.

1. Install and activate Wordfence.
2. Open **Wordfence → Firewall → Optimize Wordfence Firewall**.
3. Select **NGINX**.
4. Download the backup files offered by Wordfence.
5. Continue the optimization and wait up to five minutes.
6. If Wordfence still shows Basic Protection, restart only the `wordpress`
   service in Coolify and check again.

Wordfence creates these files inside the persistent `wordpress_data` volume:

```text
/var/www/html/.user.ini
/var/www/html/wordfence-waf.php
```

Do not copy these two generated files into the Docker image or Git repository.
The PHP image explicitly enables `.user.ini`, while Nginx blocks both files from
public HTTP access. The Nginx real-IP configuration also restores the visitor
address forwarded by Coolify so Wordfence does not block the proxy address.

Verify that both public URLs return `403` or `404`:

```text
https://example.com/.user.ini
https://example.com/wordfence-waf.php
```

The Wordfence Firewall page should eventually show **Extended Protection**.

## Important operations notes

- Keep `WP_DEBUG=false` in production.
- Production debug-file logging and unfiltered administrator HTML are disabled.
- WordPress minor core security updates remain enabled.
- Trash is retained for 30 days and post revisions are limited to 10.
- Back up `wordpress_data` because it contains uploads, plugins and themes.
- DigitalOcean database backups do not include WordPress uploads.
- Cloudflare should use **Full (strict)** SSL.
- Do not expose Redis or PHP-FPM to the public Internet.
- `DISALLOW_FILE_EDIT` disables the built-in theme/plugin editor, but normal plugin
  installation and updates remain available.

## Files changed for automatic security

- `docker-compose.yml`: generated WordPress keys/salts, process limits, init and
  bounded Docker logs.
- `nginx/nginx.conf`: prevents authenticated requests from entering FastCGI cache.
- `nginx/default.conf`: security headers, removal of PHP signature and prevention
  of responses containing `Set-Cookie` from entering cache.
- `.env.example`: local placeholders for Coolify-generated keys and salts.
- `README.md`: deployment and security notes.
- `V4-CHANGES.md`: V4 change record.

## Files changed for Wordfence

- `php/conf.d/99-wordpress.ini`: explicitly enables `.user.ini` with a five-minute
  refresh interval.
- `nginx/default.conf`: blocks `.user.ini`, `wordfence-waf.php`, sensitive backup
  files and PHP execution in upload/cache directories.
- `nginx/nginx.conf`: restores the visitor IP received through Coolify.
- `README.md`: Wordfence optimization and verification steps.
- `V4-CHANGES.md`: Wordfence change record.

No Wordfence-specific change is required in `docker-compose.yml`.
